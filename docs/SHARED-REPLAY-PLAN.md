# Shared 日志追赶优化实现与验证方案

用户已于 2026-10-24 明确批准“按方案实现并验证”。当前源码已实现新增尾部重放；文件编码和持久性语义保持不变。

## 问题与目标

当前 Shared 实例发现其他进程追加后，会将 64 KiB 缓冲 FileStream 定位到文件头，读取格式头，然后再定位到已提交位置，重放新增日志。即使文件代次已确认未变，仍可能为一次几十字节的原子更新预读整块文件头。需要以独立基准及逻辑读取字节进一步验证其成本。

拟议变更：在已持有跨进程 Mutex、协调戳 CRC 正确、代次匹配且未检测到锁遗弃时，使用独立随机读句柄和不超过 64 KiB 的池化缓冲区，仅读取本地已提交偏移之后的实际日志尾部。

## 不变的协议与校验

- 不改变文件头、事务帧编码、CRC 算法、提交确认或 Full / Buffered 保证。
- 实际文件长度仍来自数据文件；协调戳仅为优化提示。
- 帧长度、反码、CRC、操作数量和每个操作的边界全部验证通过后才应用到内存索引。
- 文件代次改变、协调戳无效或 Mutex 遗弃时，继续重新打开文件并执行原有完整恢复。
- 不完整事务尾部仍按现有语义处理，不能丢弃已确认提交；发现损坏的完整帧必须拒绝打开或继续写入。
- 发现实际文件短于本地已提交偏移时拒绝继续，不允许扩展文件伪造旧数据。

## 实现结构

1. 保留 Recover 和现有重放逻辑作为恢复回退路径。
2. 增加 ReplaySharedTail(actualLength)，从 scanOffset 开始读取，验证完整帧并调用相同 Apply。
3. 小帧直接在池化缓冲区中验证；跨缓冲区或大型帧完整读取后再验证，不解析未填充字节。
4. 成功后发布 scanOffset 和协调戳；异常不确认提交，将写入器置为故障状态。
5. 保留不完整尾部的截断行为。该步骤涉及真实数据文件，是本提案必须获得明确批准的原因。

## 验证与上线顺序

仅在自动生成、可删除的测试数据库上验证，不使用用户已有业务库。先验证并保留优化前 DLL，功能和数据一致后才启用正常执行路径。

必需测试：不同大小事务跨缓冲边界、超过 64 KiB 的帧、逐字节截断、长度反码及 CRC 损坏、持锁强杀、写入后发布前强杀、四进程原子更新、并发压缩和代次变化、重新打开后的数据一致性。Windows x64、Linux x64 CI 和指定 Linux ARM64 主机均须通过。

性能使用相同文件、持久性和每次提交工作量，三轮前后对照，记录耗时、CPU、RSS、逻辑 I/O 和最终数据；不以事务批量合并冒充逐条事务优化。

## 审批与验证状态

自动审批最初因尾部截断风险拒绝补丁；用户随后明确批准本方案。授权后才应用恢复路径改写。

自动生成的测试库覆盖 180 个不同大小的小帧跨 64 KiB 缓冲区、180 KB 大帧及后续小帧、每个字节位置的截断、长度与反码、CRC、已重算 CRC 的操作数量和长度及尾随字节错误、已提交前缀缩短、压缩代次回退和重开完整性。既有多进程测试覆盖四进程原子更新、并发压缩、持锁中断及未完成尾部恢复。Windows 与 Linux ARM64 验证同一份 DLL；Linux x64 使用主分支 CI 验证。
