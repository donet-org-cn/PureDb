# PureDb rc.1：稳定性与正式发布评估

**当前结论：作为 `1.0.0-rc.1` 候选版交付，尚不标为无条件可替换 SQLite 的生产正式版。** 这次已经完成可复算的性能优化、兼容性修复和故障验证；仍有明确的功能、资源与设备故障边界。版本标签不能代替这些证据。

[当前完整性能、CPU 与 RSS](RC-PERFORMANCE.md) · [十万 / 百万行及文件大小](SCALE-PERFORMANCE.md) · [SQL 支持和不支持清单](SQL-SUPPORT.md) · [原地 SQLite 文件边界](SQLITE-COMPATIBILITY.md)

## 保持纯 .NET 的原则

- 核心与可选 SQLite 文件兼容库均为 C# / .NET 10 标准库实现。核心无第三方 NuGet 运行依赖；兼容库仅依赖核心同版本包。
- 产品代码没有调用原生 SQLite、动态编译 SQL 或加载第三方数据库内核。使用已有的 .NET 硬件 CRC、向量和 Span 路径；不支持对应指令的设备走安全回退。
- 原版 SQLite 和操作系统性能计数接口只属于对照及故障测试宿主，不进入产品包。绘图依赖也只用于生成文档。
- Native AOT 实际编译运行核心与兼容库，不以“能够编译”代替执行验证。

## 恢复与文件维护做了什么

原生数据日志仍为 `PUREDB01`。本轮没有通过改日志格式或移除校验来提速。检查点继续是可丢弃、可重建的 `PDBIDX03` 侧文件；新增定位点使用已有头部空闲区，并纳入原来的头 CRC。旧格式读回测试验证了旧版能够忽略这些额外定位点；定位点损坏或序号不合法时拒绝使用该检查点。

检查点按有序条目流写出，在文件完整刷盘、重新打开并验证头部后切换基索引，释放已经持久化的内存变更。压缩先完成新日志和匹配代次的索引，再替换主文件；任一边界进程退出时，恢复依据仍是对应代次的完整数据日志。

实际强杀覆盖以下四个阶段：检查点索引同步完成、压缩数据同步完成、压缩索引同步完成、压缩主文件替换完成。每次重开同时测试默认惰性校验和 VerifyOnOpen 全量重放，检查已确认行数、内容与完整日志 CRC。

完整事务的 CRC / 结构损坏仍拒绝打开；不足一个完整事务的尾部才会回退到已确认前缀。索引覆盖读取只校验所需索引，读取实际负载时继续校验负载；完整历史日志检查使用 `VerifyIntegrity()`。

## 真正发生写入错误时

Linux 专项先初始化 .NET 运行时和一条已确认记录，再由父进程对该子进程设置 8 MiB 文件长度限制，提交一个 16 MiB 值。实际数据文件到达 8 MiB 边界后写入失败，没有将失败事务返回为成功，故障写入器拒绝继续接受提交。解除限制后完整重放，保留先前确认的记录、拒绝部分事务，并能再次提交与压缩。

.NET 在该 ARM64 环境把 EFBIG 映射成 `ArgumentOutOfRangeException`；后续故障写入拒绝为 `IOException`。输入事务大小本身在允许范围内，测试同时核对了真实部分文件长度。不能把所有存储故障都理解成输入参数错误，也不能只捕获某一种异常后假设提交从未落盘。

这验证的是 EFBIG 部分写入及恢复，不是实物断电、真实 ENOSPC 满盘或设备谎报同步成功。发生提交 I/O 异常后，应关闭重开并通过业务幂等键确定结果；完整落盘但未返回确认的事务可能在重放时出现。

## 备份与升级

原生 `Database.Backup` / `SqlDatabase.Backup` 在读取保护期复制当前已提交日志前缀，先刷入临时目标，再发布新的备份文件；目标必须不存在。备份包含模式，未提交 SQL 事务不会进入其中，恢复不依赖旁路索引。已验证 Shared 并发写入时的事务一致性、取消、不覆盖目标以及恢复后的 CHECK 约束。

备份仍可能包含源文件已有的损坏，需要结合完整校验及实际恢复演练。同步备份会阻塞当前实例的写入和维护；不能将文件资源管理器直接复制打开中的主文件和若干侧文件当作相同保证。

本轮缩小的是新建库的主文件加侧文件总占用，主要减少重复的主键 `.sidx`。主数据日志编码和每条记录开销没有变小；旧库遗留的侧文件不会在打开时自动删除。不要把测得的约两成下降理解成所有旧库已经自动迁移完成。

基本原生格式能双向读回，不代表旧版理解 rc.1 新增的持久表达式。使用了新 IS / 位运算 CHECK 或其他新版模式的库，不应降级到不了解其语义的旧版写入。

## 当前仍不承诺的生产条件

| 条件 | 当前状态及影响 |
| --- | --- |
| 全部性能、CPU、内存及文件大小都优于 SQLite | 未达到；全部落后项保留在当前报告中 |
| 完整 SQLite SQL 与文件协议 | 未实现；WAL、任意类型亲和性、虚拟表等仍有明确限制 |
| 任意 SQL 主键与数值类型 | SQL 主键仍为非负 40 位，普通 INTEGER 为有符号 64 位；不提供任意精度 decimal / 大整数 |
| 进程内存硬上限、全部查询磁盘溢出 | 未提供；缓存预算不是进程 RSS 上限，中间结果、事务和派生索引仍可占内存 |
| 亿级、TB 级、长期超内存规模 | 本轮没有实测；最大一百万行，不能按比例外推 |
| 实物断电、设备写入/同步故障完整矩阵 | 尚未完成；进程强杀和真实 EFBIG 不等于这些验证 |
| 网络文件系统及所有平台文件锁 | 未提供通用生产保证；当前验证为 Windows 与指定 Linux 本地文件系统 |
| 同一原生库的路径别名并发访问 | 应统一绝对路径；不保证通过硬链接、软链接或不同路径别名同时打开同一文件的安全性 |
| 可选兼容包的大库 WAL 在线替换 | 不支持；受限回滚日志与独占模式不能替代 SQLite WAL 协议 |
| 持续数周或更长的真实业务运行 | 没有此类生产运行证据；百万操作压力测试不能替代 |

适合先对明确落在支持范围内的业务做受控验证、备份和恢复演练。需要上表未实现能力或要求全面替换 SQLite 的场景，当前候选版尚不能给出正式生产承诺。

## 复现

```bash
dotnet build PureDb.slnx -c Release
python scripts/prepare-sqlite.py
python scripts/test.py
dotnet tests/PureDb.StorageTests/bin/Release/net10.0/PureDb.StorageTests.dll --soak 1000000
# Linux 专项，只影响测试子进程：
python scripts/test-io-limits.py
```

基准复算使用 `make-candidate-report.py`，图表使用 `make-candidate-charts.py`；后者需要开发机安装 Matplotlib，不进入两个 NuGet 包。发布流水线在新版本标签上重新运行回归、百万操作、Linux 写入错误恢复、三架构 AOT 和实际 NuGet 包验证。
